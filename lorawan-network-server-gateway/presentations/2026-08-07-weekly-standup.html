OS Baseline Evolution

Why we migrated: Raspberry Pi OS Lite → Gateway OS Base

Transitioning from a general-purpose Linux prototype to a power-loss safe, field-hardened OpenWrt edge baseline.

Prototype Baseline

Raspberry Pi OS Lite (Debian)

  • Power-Loss Vulnerability: Uses a standard read-write ext4 root filesystem. Sudden field power cuts easily corrupt system files and brick the SD card.
  • Manual Build Overhead: Required manually building C driver libraries (sx1302_hal), setting up custom systemd unit files, and wiring SPI reset pins.
  • Resource Bloat: General-purpose Debian runs background daemons, systemd overhead, and unnecessary packages (~150–250 MB RAM usage).
Production Baseline Standard

ChirpStack Gateway OS Base (OpenWrt)

  • Power-Loss Safe (SquashFS + OverlayFS): Immutably read-only root OS filesystem. System files remain 100% immune to abrupt power loss in field operations.
  • Pre-Packaged C/Rust Daemons: Ships with native ChirpStack concentratord (Rust driver for SX1303 via SPI) and mqtt-forwarder managed via LuCI GUI & uci.
  • Minimal Footprint (Base Variant): Minimalist OpenWrt footprint (~30–50 MB RAM, sub-10s boot). Base variant excludes heavy local server stacks.
Migration Result: Gateway OS Base provides a zero-maintenance, crash-resilient edge appliance foundation while connecting to external ChirpStack server infrastructure over mTLS.

Edge Architecture

Detailed gateway store-and-forward data path

Actual daemon pipeline running on ChirpStack Gateway OS Base for outage resilience.

RAK5146 Concentrator Raw SPI /dev/spidev0.0
Concentratord Daemon IPC ipc:///tmp/concentratord
MQTT Forwarder Protobuf @ 127.0.0.1:1883
Mosquitto Queue mosquitto.db queue
mTLS Bridge ssl://:8883

What this Edge Pipeline Guarantees

  • Concentratord Ownership: Single Rust daemon owns SX1303 hardware via SPI interface.
  • Offline Uplink Buffering: Local Mosquitto stores uplinks on disk during WAN outages.
  • Replay Capability: Queued uplinks auto-flush to server upon internet restoration.
  • mTLS Egress: Authenticates via CA.crt + Gateway.crt (CN=).

Key Operational Rules

  • Loopback Isolation: Local MQTT listener bound strictly to 127.0.0.1:1883.
  • Topic Prefix: Uplinks published to as923/gateway//event/up (QoS 1).
  • Non-Persistent Downlinks: Downlinks use QoS 0 to meet receive window timing.
  • No Direct WAN MQTT: Forwarder publishes to local broker, never directly to WAN.

etcd — consensus store & quorum

Distributed key-value store maintaining cluster state for Patroni.

Role in the MDS Architecture

etcd acts as the Distributed Consensus Store (DCS) for Patroni. It resolves a single critical question:

"Which Spilo node currently owns the active Patroni leader lock TTL?"
Raft Consensus Protocol Ports :2379 / :2380
Metadata Namespace /service/spilo-cluster
SQL Path Isolation 0 Payload Overhead
💡 ARCHITECTURAL ROLE

The distributed source of truth—holding the active Patroni leader lock TTL key in shared memory so nodes reach Raft consensus without split-brain conflicts.

Why 3 Members are Required for Quorum

Raft relies on strict majority voting: Quorum = (N/2) + 1

3-Member etcd Cluster: Quorum = 2 · Tolerates 1 Node Loss
2-Member etcd Cluster: Quorum = 2 · Tolerates 0 Node Loss
Raft Majority Rule 2 of 3 member votes required
Fault Tolerance Survives 1 etcd node failure

HAProxy — primary-aware SQL router

Layer 4 TCP load balancer dynamically routing SQL traffic to the active leader.

Leader-Aware Routing Mechanism

HAProxy listens on TCP port :5432 and routes SQL traffic exclusively to whichever Spilo node reports itself as Patroni leader.

HAProxy HTTP Health Check Rule:

Queries http://<spilo-ip>:8008/primary every 2 seconds.

• Returns HTTP 200 → Node marked ACTIVE backend target.

• Returns HTTP 503 → Node dropped from backend pool instantly.

Why HAProxy is Essential

Provides strict Layer 4 isolation between database failover state and application clients.

Prevent Write Misrouting Blocks writes to Replicas
Zero DNS Caching Lag Fixed TCP Port :5432
Sub-2s Target Switch Instant L4 Switchover
💡 ARCHITECTURAL ROLE

The primary-aware SQL traffic router—polling Patroni HTTP health endpoints (:8008/primary) to ensure SQL writes land strictly on the active leader node.

Automated PostgreSQL 5-step failover sequence

Sequence executing automatically when a primary leader node drops offline.

Step 01

Leader Drops

Active Primary Spilo node crashes or suffers host network isolation.

Step 02

Lock Expires

Patroni TTL leader lock key in etcd expires after 10s missing heartbeat.

Step 03

Replica Promoted

Patroni standby nodes hold Raft election via etcd and promote safest replica.

Step 04

HAProxy Shifts

HAProxy health check on :8008/primary passes on promoted node; traffic shifts.

Step 05

Pool Reconnects

PgBouncer clears broken server connections and re-establishes pool through HAProxy.

Recovery Standard: ChirpStack database write operations recover within 5 seconds without altering DSN configuration files.
