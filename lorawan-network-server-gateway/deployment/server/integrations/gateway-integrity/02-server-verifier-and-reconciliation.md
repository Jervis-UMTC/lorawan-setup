# 2. Server Verifier, Reconciliation, and Evidence Gate

This guide defines the server roles and database state needed to turn uploaded gateway evidence into a verification result.

> [!IMPORTANT]
> The repository does not currently contain completed images for these roles. Names such as `gateway-evidence-verifier` describe responsibilities, not deployable images. Production requires reviewed source/builds, pinned immutable digests, startup self-tests, and the tests in the next guide.

## 2.1 Separate the roles

```text
Evidence ingestor
  receives checkpoints and closed segments
  authenticates gateway upload identity
  stores receipt metadata and evidence objects

Gateway MQTT evidence collector
  subscribes read-only to remote gateway event topics
  preserves delivered gateway-event evidence

Evidence verifier
  validates record/segment chains
  validates checkpoint continuity
  correlates journal vs MQTT
  links the accepted ChirpStack application event
  runs/calls the pinned trusted decoder
  writes verification result
```

The verifier must not own OpenBao sign credentials or a Fabric client identity.

## 2.2 Server data path

```text
Gateway journal uploader
       |
       v
Evidence ingest API
       |
       +-> checkpoints
       +-> segment metadata
       +-> immutable segment object
       |
       v
Evidence verifier <----------------------+
       ^                                  |
       |                                  |
Gateway MQTT evidence collector          |
       ^                                  |
       |                                  |
remote MQTT broker                       |
       |                                  |
       +-> ChirpStack -> application MQTT-+
```

Large raw evidence stays in a protected evidence store. PostgreSQL contains indexes, hashes, identities, status, and references.

## 2.3 PostgreSQL schema

Create a separate schema in the telemetry database:

```sql
CREATE SCHEMA IF NOT EXISTS gateway_evidence;
```

### Checkpoints

```sql
CREATE TABLE IF NOT EXISTS gateway_evidence.checkpoints (
    checkpoint_id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    gateway_id           TEXT NOT NULL,
    checkpoint_version   TEXT NOT NULL,
    segment_id           BIGINT NOT NULL,
    last_sequence        BIGINT NOT NULL,
    last_record_hash     TEXT NOT NULL,
    segment_hash         TEXT NOT NULL,
    gateway_created_at   TIMESTAMPTZ NOT NULL,
    server_received_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    client_identity      TEXT NOT NULL,
    request_id           TEXT,
    checkpoint_digest    TEXT NOT NULL,
    CONSTRAINT gateway_checkpoint_hash_ck CHECK (
      last_record_hash ~ '^[0-9a-f]{64}$'
      AND segment_hash ~ '^[0-9a-f]{64}$'
      AND checkpoint_digest ~ '^[0-9a-f]{64}$'
    ),
    UNIQUE (gateway_id, last_sequence)
);
```

A conflicting retry must be rejected before an upsert could replace the original hash.

### Uploaded segments

```sql
CREATE TABLE IF NOT EXISTS gateway_evidence.segments (
    segment_row_id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    gateway_id            TEXT NOT NULL,
    segment_version       TEXT NOT NULL,
    segment_id            BIGINT NOT NULL,
    first_sequence        BIGINT NOT NULL,
    last_sequence         BIGINT NOT NULL,
    record_count          BIGINT NOT NULL,
    previous_segment_hash TEXT NOT NULL,
    final_record_hash     TEXT NOT NULL,
    segment_hash          TEXT NOT NULL,
    object_ref            TEXT NOT NULL,
    object_sha256         TEXT NOT NULL,
    uploaded_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    verify_status         TEXT NOT NULL DEFAULT 'pending',
    verify_error          TEXT,
    CONSTRAINT gateway_segment_status_ck CHECK (
      verify_status IN ('pending','verified','evidence_gap','integrity_failure')
    ),
    UNIQUE (gateway_id, segment_id)
);
```

`object_ref` points to the immutable uploaded segment object/file. In the one-VM lab this can be a protected persistent volume. Production should use independently backed durable evidence storage.

### Captured gateway MQTT events

```sql
CREATE TABLE IF NOT EXISTS gateway_evidence.mqtt_gateway_events (
    gateway_event_id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    gateway_id               TEXT NOT NULL,
    mqtt_topic               TEXT NOT NULL,
    broker_received_at       TIMESTAMPTZ NOT NULL,
    serialized_event_sha256  TEXT NOT NULL,
    phy_payload_sha256       TEXT,
    uplink_id                TEXT,
    frequency_hz             BIGINT,
    rssi_dbm                 INTEGER,
    snr_db                   DOUBLE PRECISION,
    collector_version        TEXT NOT NULL,
    object_ref               TEXT
);
```

Preserve the exact serialized event outside the row when forensic replay requires it.

### Per-application-event verification

```sql
CREATE TABLE IF NOT EXISTS gateway_evidence.event_verification (
    verification_id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    source_event_key         TEXT NOT NULL,
    observed_at              TIMESTAMPTZ NOT NULL,
    gateway_id               TEXT,
    journal_segment_id       BIGINT,
    journal_sequence         BIGINT,
    journal_record_hash      TEXT,
    journal_segment_hash     TEXT,
    checkpoint_id            BIGINT,
    gateway_event_id         BIGINT,
    decoder_id               TEXT,
    decoder_version          TEXT,
    raw_app_data_sha256      TEXT,
    normalized_digest_sha256 TEXT,
    status                   TEXT NOT NULL DEFAULT 'pending',
    reason_code              TEXT,
    verified_at              TIMESTAMPTZ,
    created_at               TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at               TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT gateway_event_verification_status_ck CHECK (
      status IN ('pending','verified','evidence_gap','integrity_failure','not_required')
    ),
    UNIQUE (source_event_key, observed_at)
);
```

Keep payload objects in evidence/object storage and telemetry tables; this row is a lineage index.

## 2.4 Least-privilege roles

### Evidence ingestor

```text
API: authenticate each gateway
DB: insert checkpoints/segment metadata
Evidence store: create new objects; no overwrite where supported
```

### Gateway MQTT evidence collector

```text
Broker: subscribe to gateway event topics only
DB: insert capture indexes
Evidence store: create captured-event objects
Publish: denied
```

### Evidence verifier

```text
DB: read evidence + telemetry; update only verification status/results
Evidence store: read
Broker publish: denied
OpenBao sign: denied
Fabric client identity: none
```

Verification and evidence signing remain different trust functions.

## 2.5 Evidence upload API

Target API shape:

```text
https://evidence.<DOMAIN>/v1/gateways/<GATEWAY_EUI>/checkpoints
https://evidence.<DOMAIN>/v1/gateways/<GATEWAY_EUI>/segments/<SEGMENT_ID>
```

Freeze the real route contract before implementation.

Require:

- TLS hostname validation;
- mutual TLS or equivalently strong per-gateway machine identity;
- one upload identity mapped to exactly one Gateway EUI;
- body-size limits;
- exact idempotent retry;
- conflict rejection for same identity with a different digest;
- no overwrite API for accepted checkpoints/segments;
- recovery rate limits large enough for a legitimate outage backlog.

## 2.6 Verify an uploaded segment

For each closed segment:

1. Verify the uploaded object's SHA-256.
2. Parse only the exact supported segment version.
3. Verify request Gateway EUI and segment identity match content.
4. Verify first/last sequence and record count.
5. Recompute every RFC 8785 record hash.
6. Verify each `previous_record_hash` link.
7. Recompute the segment hash using the frozen byte contract.
8. Verify `previous_segment_hash` against the preceding verified segment/checkpoint lineage.
9. Mark `verified` only after every required check passes.
10. Mark contradictory bytes/hashes `integrity_failure`.
11. Mark unavailable required prior evidence `evidence_gap` when contradiction was not proven.

Never repair an uploaded segment in place.

## 2.7 Correlate journal to the captured remote MQTT event

The verifier must find exactly one counterpart.

Prefer identical source-event digest when the two implementations preserve the same upstream serialized representation. Otherwise match using the versioned rule built from:

```text
gateway ID
PHYPayload digest
uplink identifier/context when available
frequency and bounded receive time when needed
```

Outcomes:

```text
one exact match     -> continue
zero before expiry  -> pending
zero after expiry   -> evidence_gap
multiple candidates -> ambiguous; do not guess
conflicting payload -> integrity_failure
```

## 2.8 Link to the ChirpStack application event

Preserve the application identity already used by the telemetry pipeline:

```text
source_event_key
observed_at
deduplicationId when available
DevEUI
DevAddr/session identity when available
fCnt
fPort
rxInfo gateway IDs
```

Prefer a direct documented correlation identifier from the pinned ChirpStack release. Otherwise define and version a unique composite. Timestamp-only matching is prohibited.

## 2.9 Trusted decoder comparison

For evidence-selected events:

1. Preserve ChirpStack raw application `data` or its digest.
2. Run the pinned independent decoder.
3. Produce a deterministic normalized metric object.
4. Canonicalize/hash the normalized result under its versioned contract.
5. Query the matching TimescaleDB row by `source_event_key + observed_at`.
6. Compare the approved normalized fields and decoder identity.
7. Mark a material mismatch `integrity_failure`.

Node-RED still performs operational normalization. This additional check prevents a Node-RED flow from being the only evidence authority.

## 2.10 Gate Fabric v2 on verification

Keep historical `telemetry-attestation-v1` behavior unchanged.

The journal-aware path is:

```text
telemetry-attestation-v2
```

Before the Fabric adapter claims/seals a v2 event, require a matching verification row with:

```text
status = verified
```

Conceptual claim filter:

```sql
AND (
  o.schema_version <> 'telemetry-attestation-v2'
  OR EXISTS (
    SELECT 1
    FROM gateway_evidence.event_verification AS v
    WHERE v.source_event_key = o.source_event_key
      AND v.observed_at = o.observed_at
      AND v.status = 'verified'
  )
)
```

The adapter must not update the verification state itself.

If the status is:

```text
integrity_failure
  -> security-conflict/dead-letter procedure

evidence_gap
  -> business policy decides delay/reject/explicit incomplete attestation

pending
  -> remain ineligible for v2 sealing
```

Do not relabel an evidence gap as verified merely to drain the queue.

## 2.11 Compact v2 gateway-evidence projection

`telemetry-attestation-v2` can add:

```json
{

    "status": "verified",
    "verification_id": 12345,
    "gateway_id": "0000000000000001",
    "journal_segment_id": 53,
    "journal_sequence": 52987,
    "journal_record_hash": "<64_HEX>",
    "journal_segment_hash": "<64_HEX>",
    "checkpoint_id": 812,
    "gateway_event_id": 99123,
    "decoder_id": "<PINNED_DECODER_ID>",
    "decoder_version": "<PINNED_DECODER_VERSION>",
    "raw_app_data_sha256": "<64_HEX>",
    "normalized_digest_sha256": "<64_HEX>"
  }
}
```

The full segment remains off-chain. The existing OpenBao seal and Fabric envelope protect the canonical v2 evidence after verification.

## 2.12 Recovery order after WAN outage

```text
1. MQTT bridge reconnects and drains queued gateway events.
2. Journal uploader sends missing segments/checkpoints.
3. Verifier proves segment continuity from the latest cloud anchor.
4. Verifier correlates journal records with captured gateway MQTT events.
5. Verifier links accepted ChirpStack application events.
6. Trusted decoder is compared with TimescaleDB.
7. Result becomes verified / evidence_gap / integrity_failure.
8. Only verified v2 events become eligible for OpenBao/Fabric sealing.
```

Telemetry may remain queryable while evidence is pending. Dashboards must not present `pending` as the same thing as cryptographically verified history.
