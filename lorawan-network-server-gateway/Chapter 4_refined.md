# CHAPTER IV
# RESULTS AND DISCUSSION

Chapter 4 presents the results obtained from the final dissertation test arrangement described in Chapter 3. The counted data must be reported from retained evidence generated by the assembled EMU-01 physical Agriculture Kit node over the real AS923 LoRaWAN path. SEC-02 is used only for the defined invalid-device, replay, and spoofing conditions. Sensor values may change naturally; record matching and continuity are established through the frozen payload-v2 contract, EMU-01 sequence, frame counter, stable event identity, and timestamps.

The final test architecture differs from both the earlier all-in-one Raspberry Pi design and the later single-VM laboratory draft. The Raspberry Pi 4B and RAK5146 operate as Gateway-01. Its SIM7600 LTE link is the health-gated primary cloud backhaul, Wi-Fi is the automatic fallback, and Ethernet is reserved for management/recovery. ChirpStack and the application/control-plane services run on the commissioned three-node DigitalOcean Ubuntu Server POC. This separation must be reflected consistently in performance, security, and resilience results: Gateway-01 resource use is distinct from cloud-node resource use, and the external Hyperledger Fabric network is a downstream dependency rather than a local service.

## 4.1 Prototype Design and Implementation

This section answers Problem 1 by describing the final implemented prototype and explaining why the test arrangement was organized in this form.

The prototype used two RAK4631 WisBlock Core modules, the installed Agriculture Kit sensor modules on EMU-01, Gateway-01 (Raspberry Pi 4B + RAK5146 + SIM7600 LTE), a separate test workstation, and the commissioned three-node DigitalOcean Ubuntu Server POC. EMU-01 served as the registered physical-sensor OTAA node and transmitted the frozen 46-byte payload-v2 containing sequence, uptime, soil, UV, barometric, light, environmental, rain, battery, and validity fields. SEC-02 remained isolated from EMU-01 credentials and was used only for the authorized wrong-AppKey, unregistered-device, replay, and invalid-MIC fixtures.

The monotonic EMU-01 sequence and stable network/application identities allowed the expected order of legitimate transmission attempts to be tracked even though the physical sensor values themselves changed naturally. This made missing, duplicated, modified, and incorrectly ordered records observable without fabricating the measurement source. The test retained the real sensor interfaces, OTAA, AS923 RF link, RAK5146 gateway, ChirpStack security checks, payload decoder, and downstream application path.

The Raspberry Pi gateway used ChirpStack Gateway OS Base, ChirpStack Concentratord, MQTT Forwarder, and a local Mosquitto broker. MQTT Forwarder published Protobuf gateway messages at QoS 1 to the loopback broker. The local broker maintained a bounded persistent queue and bridged gateway traffic to the server through mutual TLS. This design gave the gateway a simple store-and-forward capability while keeping the local broker unavailable to ordinary LAN clients. The gateway was treated as a transport and availability component; LoRaWAN authentication remained the responsibility of ChirpStack on the server.

The server-side dissertation testbed uses the actual commissioned three-node DigitalOcean POC rather than a reduced single-VM simulation. Each node uses the 1-vCPU/2-GiB Ubuntu Server 24.04 profile. The cloud control/application plane is therefore measured as three small cooperating nodes rather than as one larger local VM.

The commissioned stack includes etcd, Patroni/Spilo PostgreSQL with TimescaleDB, HAProxy, PgBouncer, Mosquitto, Valkey/Sentinel, two ChirpStack instances, OpenBao, Node-RED, Grafana, gateway-evidence services, and the two Fabric-adapter workers in fail-closed standby until external activation. Chapter IV measures the system that actually generated the evidence; it does not exclude HA or security components merely to reduce the reported resource baseline. Raw per-node resource observations must remain available so an aggregate result cannot conceal one overloaded node.

Accepted ChirpStack application events were first passed through Node-RED and only then written to PostgreSQL/TimescaleDB. Node-RED served as the application-ingestion gate: it validated required identity and timestamp fields, normalized the reviewed sensor fields, derived the stable event identity, used parameterized SQL, and relied on the database transaction and uniqueness constraints to prevent partial or duplicate operational records. These are application and database-safety controls; Node-RED was not the production cryptographic signer.

Selected events also created durable Fabric outbox records in the same database transaction as telemetry ingestion. The Fabric adapter processed the outbox asynchronously, constructed the approved canonical evidence from the stored source fields, calculated SHA-256, and used OpenBao for cryptographic sign/verify operations. Complete raw telemetry and canonical evidence remained off-chain. The external Hyperledger Fabric transaction contained the stable event identity and compact attestation proof: schema version, event type, digest, OpenBao signature algorithm, signing-key version identifier, and complete versioned signature. This separation prevented Fabric unavailability from blocking normal telemetry storage and allowed later database changes to be detected by recomputing the approved evidence digest and comparing it with the committed attestation.

The complete measured path was therefore:

`RAK4631 EMU-01 -> real AS923 LoRaWAN RF -> RAK5146 + Raspberry Pi 4B -> Concentratord -> MQTT Forwarder -> gateway Mosquitto persistent buffer -> mTLS over SIM7600 LTE (Wi-Fi fallback) -> DigitalOcean Reserved IPv4 -> cloud Mosquitto/HA path -> ChirpStack -> Node-RED -> Patroni PostgreSQL/TimescaleDB -> Fabric outbox -> Fabric adapter -> OpenBao -> external Hyperledger Fabric.`

The discussion for this section should emphasize that the dissertation testbed is the commissioned three-node HA proof of concept. It is intentionally small in capacity but is not artificially stripped of the HA and security components that were actually running during the measurements. This keeps the reported LoRaWAN, messaging, storage, integrity, blockchain, and resource results tied to the system that generated them.

### Staged counted-execution rule

The test layers are methodologically independent where their decision points are independent. The 30 LoRaWAN authentication attempts in Table 12 and all 40 replay/spoofing attempts may be collected before external Fabric activation once the dedicated LoRaWAN preflight reports `LORAWAN_TRACK_STATUS=GO`. These trials are decided by Gateway-01/ChirpStack and are retained as final counted LoRaWAN evidence; they are not rerun merely because Fabric is activated later. The complete 90-attempt authentication table remains incomplete until its MQTT and Fabric parts are later performed.

The final normal-operation baseline, Fabric transaction-success rate, post-storage Fabric integrity, database-to-Fabric traceability, and resilience/recovery remain blocked until the full-stack preflight reports `SENSOR_PREFLIGHT_STATUS=GO`. This staged order prevents an unrelated external Fabric handoff from delaying valid LoRaWAN security measurements while preserving the prerequisites of every Fabric-dependent result.

### 4.2.1 Packet-Delivery Rate

`PDR (%) = (unique legitimate uplinks accepted by ChirpStack / scheduled EMU-01 transmission attempts) × 100`

### 4.3.3 Data-Integrity Test

### 4.3.6 Resilience and Recovery Test

This section presents the results of the **external Fabric-reachability interruption and recovery test**. The live Gateway-01-to-cloud LoRaWAN path itself depends on Internet/LTE connectivity, so removing all Internet access would test loss of the production transport rather than isolation of the downstream blockchain dependency.

The counted experiment must instead isolate the external blockchain dependency. Gateway-01 LTE/public MQTT ingress, the DigitalOcean Reserved-IP path, the three cloud nodes and their private VPC, ChirpStack, Node-RED, TimescaleDB, OpenBao, and the Fabric outbox remain available while only the active Fabric-adapter workers' reachability to the external Fabric endpoint is deliberately blocked using a pre-rehearsed rule. During the interruption, legitimate LoRaWAN telemetry must continue to reach TimescaleDB while Fabric work accumulates in a retryable state. After the block is removed, queued work must reconcile without conflicting duplicate ledger state.

Each of the three resilience runs retains 30 minutes of normal operation, 60 minutes of external-Fabric interruption, and 30 minutes of recovery. Using the frozen 15-second counted-test cadence profile, approximately 120, 240, and 120 normal uplinks are expected in those phases respectively, or about 1,440 across three complete runs. This experiment remains blocked until the real Fabric path is first commissioned and a healthy confirmed transaction is proven; recovery cannot be validly measured against a dependency that has never reached a normal state.

## Guidance for Final Discussion

The final discussion should connect the measured results directly to the research problems rather than treating every technology as a separate success. For performance, explain whether the commissioned three-node POC kept pace with the **15-second counted-test source profile** and note that this profile is an experiment-only timing configuration distinct from the accepted production scheduler. For security, explain which layer made each allow-or-deny decision and whether invalid input propagated beyond that layer. For integrity and traceability, explain how the monotonic source identity and Fabric evidence made changes or missing links observable. For resilience, distinguish local telemetry continuity from delayed external blockchain confirmation.

Do not interpret an unobserved attack packet as a secure rejection, a transaction ID as a valid Fabric commit, an outbox job as a blockchain record, or cloud-node CPU as Gateway-01 CPU. These distinctions are necessary so the reported results accurately describe the final architecture that was actually tested.
