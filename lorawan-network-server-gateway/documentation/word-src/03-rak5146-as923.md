# Chapter 3 — Configure the RAK5146 Radio for AS923

## 3.1 What the RAK5146 and Concentratord do

The **RAK5146-115 SPI** is the LoRaWAN radio receiver in Gateway-01. It has a Semtech **SX1303** concentrator and connects through the Raspberry Pi HAT, not through the SIM7600 LTE modem. **ChirpStack Concentratord** is the Gateway OS service that initializes this radio, listens for EMU-01/SEC transmissions and exposes received frames to MQTT Forwarder and the independent gateway journal.

**AS923** is our regional radio setting. **SPI** is the internal Raspberry Pi-to-concentrator connection. **LoRa** is the antenna connection to sensors. **GNSS/GPS** is a different antenna connector and is not the Internet connection. The separate SIM7600 provides LTE upload after radio reception.

## 3.2 Identify the installed hardware before powering on

**Equipment:** Raspberry Pi 4B, RAK Pi HAT, RAK5146-115 **SPI** module, antenna rated **900–930 MHz**, supplied standoffs, pigtail and stable Raspberry Pi power supply.

1. Disconnect all Raspberry Pi power. Find the actual label **RAK5146-115 / SPI / 902–928 MHz** and check that the antenna supports the working 923 MHz frequencies. If the label or antenna band differs, stop: this chapter cannot certify another module.
2. Confirm the mini-PCIe-shaped radio is fully seated in the **RAK Pi HAT module socket**. Its shape does **not** make it a standard PC PCIe card; never insert it into a computer PCIe slot.
3. Inspect the HAT's **40-pin Raspberry Pi header** from the sides. It must be aligned with all pins; no row or column may be offset. The SPI interface is routed through the HAT. Do not separately hand-wire the RAK5146 directly to Raspberry Pi pins.
4. Identify the **LoRa** antenna port on the actual RAK5146 module label. Press the matching u.FL pigtail straight down; do **not** attach the LoRa antenna to the **GPS/GNSS** port. Attach the 900–930 MHz LoRa antenna before powering the radio.
5. Check that screws/standoffs are secure, cable bends are gentle and no loose metal is under the board. Then proceed to Gateway OS startup as described in Chapter 2.

## 3.3 Set the exact project radio options

**Prerequisite:** Gateway-01 is powered with the approved custom Gateway OS Base image, and your workstation is on its management network. For an already commissioned gateway, inspect the live configuration without changing it. Apply these instructions only to an approved first-time build or restoration.

1. Open **http://192.168.20.11/** in the workstation browser and sign in using the commissioned protected root credential. This is the **gateway's management interface**, not ChirpStack's separate cloud dashboard.
2. In the left menu select **ChirpStack → Concentratord**.
3. Open **Global configuration**. Turn **Enabled** on, and set **Enabled chipset** to **SX1302 / SX1303**. Do not select SX1301 or 2.4 GHz.
4. Open the **SX1302 / SX1303** tab. Match each field to the worksheet immediately below. Select **RAK - RAK5146**, **AS923**, **SPI / USB unchecked**, **GNSS checked** for the commissioned onboard GNSS and **Antenna gain 2 dBi** only while the actual installed antenna remains the verified 2 dBi installation.
5. Leave **Gateway ID override empty** on the active SX1302/SX1303 tab. The radio will report its own hardware EUI. An inactive SX1301 tab may contain old EU868 and a sample Gateway ID; **ignore those inactive values**.
6. On an already working commissioned gateway, make **no change** when all fields match. For a new or deliberately rebuilt card, click **Save & Apply once**; allow Concentratord to initialize before refreshing. Do not repeatedly click while the radio starts.

## 3.4 Confirm the frequencies and downlink settings belong to the same region

Gateway radio configuration, cloud ChirpStack and EMU firmware must agree on **plain AS923**. Do not select a plan named AS923-3, US915, AU915 or EU868 simply because a vendor tutorial uses it.

| Parameter | Project-verified basis |
|---|---|
| Cloud AS923 initial uplink frequencies | **923.2 and 923.4 MHz**, 125 kHz |
| Initial LoRaWAN data rates | DR0–DR5 (SF12 through SF7 at 125 kHz) |
| Cloud RX1 delay / DR offset | **1 second / 0** |
| Cloud RX2 frequency / data rate | **923.2 MHz / DR2** |
| Historical gateway multi-SF span | **923.2–924.6 MHz** in dated commissioning logs; **not** a freshly measured channel-by-channel inventory |
| MQTT region topic prefix | `as923` |

The first two uplink frequencies and RX values are taken from the vetted ChirpStack 4.19.1 `region_as923.toml`. They do **not** substitute for inspecting the complete **effective** concentrator channel list after the hardware is plugged in. If a frequency/RX mismatch is found, record the gateway, cloud region and EMU firmware values first; do not change just one layer.

## 3.5 Verify the actual running concentrator over SSH

**When Gateway-01 is connected:** in **Windows PowerShell**, run `ssh root@192.168.20.11` and enter the approved root credential at the prompt. The commands below run **inside the Gateway-01 OpenWrt BusyBox shell**, not in PowerShell. They inspect the radio without restarting it.

```sh
echo '=== ACTIVE RADIO SETTINGS ==='
uci show chirpstack-concentratord
echo '=== RUNNING CONCENTRATORD ==='
ps w | grep '[c]hirpstack-concentratord'
echo '=== HARDWARE STATS ==='
ubus call chirpstack-concentratord-sx1302 concentratord_stats
echo '=== LAST RADIO STARTUP ==='
logread -e chirpstack-concentratord | tail -n 65
```

**PASS:** enabled SX1302, `rak_5146`, `AS923/as923`, radio daemon present, statistics call succeeds, no repeating SPI/reset/calibration failure and the **active** startup's Gateway ID is `0016c001f139a1cb`. If the stats command says object not found, first discover the installed service name instead of reinstalling Gateway OS:

```sh
ps w | grep '[c]hirpstack-concentratord'
ls /etc/init.d/*concentratord* 2>/dev/null
```

**Do not** register the inactive SX1301 sample ID in ChirpStack. If a replacement radio has a different EUI, stop before changing certificates or topics: it requires an intentional gateway identity migration.

## 3.6 Keep one radio owner and verify forwarding to local MQTT

Concentratord owns the **SPI hardware**. MQTT Forwarder reads its supported event interface; the independent gateway journal also observes that interface. The legacy Semtech UDP packet forwarder must not simultaneously own the radio.

**Gateway-01 BusyBox shell:**

```sh
echo '=== LEGACY UDP FORWARDER ==='
uci show chirpstack-udp-forwarder
ps w | grep -E '[u]dp-forwarder|[p]acket_forwarder' || true
echo '=== MQTT FORWARDER NON-SECRET SETTINGS ==='
uci -q get 'chirpstack-mqtt-forwarder.@global[0].enabled'
uci -q get 'chirpstack-mqtt-forwarder.@mqtt[0].topic_prefix'
uci -q get 'chirpstack-mqtt-forwarder.@mqtt[0].server'
uci -q get 'chirpstack-mqtt-forwarder.@mqtt[0].qos'
echo '=== LOCAL BROKER ==='
(ss -lntp 2>/dev/null || netstat -lntp) | grep ':1883'
```

**PASS:** no active competing UDP packet forwarder; MQTT Forwarder enabled; prefix `as923`; server `tcp://127.0.0.1:1883`; QoS **1** in the corrected commissioned runtime; Mosquitto only bound to loopback `127.0.0.1:1883`. This local buffer path must **not** be replaced with a direct connection to the public broker.

**Important after a fresh reflash:** the accepted September 1 immutable factory image historically contained Forwarder QoS **0**; the later tracked overlay and commissioned writable runtime corrected it to **1**. Check the effective setting and restore the approved runtime configuration rather than assuming that the embedded image includes all later corrections.

When a sensor is later plugged in, keep an authorized EMU-01 nearby and subscribe in a **separate Gateway-01 shell**:

```sh
mosquitto_sub -h 127.0.0.1 -p 1883 -t 'as923/gateway/0016c001f139a1cb/event/#' -v
```

**PASS with real hardware:** one new gateway event arrives after EMU-01 transmits on matching AS923 frequencies. Output may be binary **Protobuf**; unreadable text is not itself a failure. With both sensor and gateway unplugged, this RF test is **deferred**, not PASS or FAIL.

## 3.7 If the radio does not work

| What you observe | First thing to inspect |
|---|---|
| No Gateway EUI, repeated SPI or reset errors | Correct SPI version, 40-pin HAT alignment and power; switch off before touching the HAT |
| Gateway EUI appears, no sensor event | LoRa vs GPS antenna port, EMU transmit state, exact frequency/SF/BW |
| RF arrives but no local MQTT event | MQTT Forwarder Concentratord backend, `as923` prefix and local broker |
| JoinRequest arrives but join cannot finish | Cloud registration/AppKey and RX1/RX2/downlink channel agreement |
| GNSS warning only | GNSS antenna/location/time; **do not assume LoRa RF has failed** |
| New board reports a different EUI | Stop: update identity-bound ChirpStack registration, MQTT mTLS/ACL and evidence source only through reviewed migration |

**Chapter 3 completion check:** correct SPI/HAT/LoRa antenna → active Concentratord `SX1302 / rak_5146 / AS923` → correct hardware EUI → no competing UDP owner → Forwarder `as923` to local QoS-1 MQTT → one real EMU-01 uplink once hardware is available.
